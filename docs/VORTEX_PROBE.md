# Vortex GPU core: measured scale probe (Yosys + slang, this machine)

What was done (all with the project's own tools): headers `VX_config.vh` / `VX_types.vh` generated by Vortex's `ci/gen_config.py` (run with the user's approval) for XLEN=32, 4 warps x 4 threads, defaults otherwise;
RTL read with Yosys + the slang SystemVerilog frontend (`read_slang`), top = the project's `VX_core_top` unit-test wrapper (single core, no AFU/command processor, graphics/tensor/raytracing units excluded);
generic `synth -top VX_core_top` (hierarchical, not flattened; no technology mapping, no placement).

| quantity | value |
|---|---|
| slang elaboration | 0 errors, 4 s |
| synthesis wall time | 846 s (14 min) |
| peak memory | 2.63 GB |
| generic cells | 627,435 |
| flip-flops | about 213,000 (202,580 DFFE_PP + 5,313 DFF_P + 1,901 DFFE_PN + sync-reset variants) |
| mux cells | 213,853 |
Raw statistics: `docs/vortex_core_synth.stat`.

Reading: one small Vortex core is already about 630k generic gates, dominated by flip-flops - the register file and cache arrays are mapped to flops because no memory macros are inferred. On sky130 that would be a very large
design (a flop is several times a NAND2); with SRAM macros (see `silicon/macros.py`, OpenRAM from the PDK) the flop count would drop but macros dominate area. The Borg core run on this machine showed the flow after
synthesis (placement/STA) is memory-bound at this scale (OOM at 13.9 GB for 380k instances), so a full P&R of even one Vortex core would need a bigger machine; synthesis alone is feasible. NOT measured: technology mapping,
timing, area in a real PDK, the effect of the FPU/extension choices (default extension set was used), multi-core, caches at realistic size.
